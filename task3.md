This is a bad idea.
This is because Board3d extending Board would imply that a Board3d is a board. This means that a Board3d is a board and can be used anywhere a Board is expected. However, this isn't the case and violates the Liskov Substitution Principle. The current board has setLocation(int x, int y) but a #D board now needs another parameter (int z). Thus, Board3D has to either keep the inherited setLocation(intx, int y) around in a form that no longer make sense as it cannot represent that new z axis. Otherwise, it needs to have a new method for 3D placement that isn't part of Board.

If Board3D keeps the setLocation(int x, int y) method, any code written against Board that calls setLocation(x, y) on what it thinks is a normal board would behave incorrectly or unpredictably if handed a Board3D.

In the other scenario of creating a brand new method, this isn't honoring or extending Board anymore and is just borrowing the name which makes it unnecessary to even extend Board. It defeats the purpose of extending Board if we are adding new functions that do fundamentally different things compared to the parent. This also could violate the Open/Closed Principle, because getting Board3D to work will likely require going back and making sure Board's methods, storage, etc. all work properly. Generally, Board3D isn't a specialized version/extension of Board and has a different use and properties which makes class inheritance the wrong tool.
